# 커밋 규칙

- 커밋 제목은 `타입: 변경 내용` 형식으로 작성한다.
- 타입은 `feat`, `fix`, `docs`, `refactor`, `test`, `chore` 중 변경 목적에 맞게 선택한다.
- 변경 내용은 한국어로 간결하게 작성한다.
- 커밋을 생성하기 전에 작성한 커밋 메시지를 사용자에게 보여주고, 명시적으로 확인을 받은 뒤 커밋한다.

| 타입 | 용도 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 작성 및 수정 |
| `refactor` | 기능 동작을 유지하는 코드 구조 개선 |
| `test` | 테스트 추가 및 수정 |
| `chore` | 의존성, 빌드 설정 등 유지보수 작업 |

## 문서 변경 이력

에이전트가 후속 작업을 할 때 정책, 요구사항, 아키텍처의 변경 이력을 Git에서 확인하고 현재 기준이 정해진 이유를 파악할 수 있도록 한다. 문서의 기준이나 설계가 바뀔 때는 커밋 제목에 무엇을 바꿨는지 쓰고, 본문에 어떤 결정을 내렸고 왜 그렇게 했는지 남긴다.

- 결정을 내리게 된 문제나 제약, 선택의 근거를 적는다. 검토한 대안이나 영향을 받는 동작이 결정에 중요했다면 함께 적는다.
- 이미 내려진 결정을 문서에 반영하는 경우에는 그 결정의 근거와 관련 구현 커밋을 적는다.
- 오탈자, 서식, 링크 정리처럼 문서의 의미가 그대로인 변경은 제목만으로 충분하다.

```text
docs: 실행 기록에 노드 반환값을 보존하는 설계 반영

시연에서 메시지와 도구 요청을 각각 표시할 수 있도록, 실행 기록에
문자열 요약 대신 노드가 반환한 값을 저장하기로 했다.
Rich 시연 출력을 구현한 010c251의 변경을 아키텍처 문서에 반영한다.
```
